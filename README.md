# regd — реестр агентных инструментов с доверием и сроком годности

[![CI](https://github.com/kostyk348/regd/actions/workflows/tests.yml/badge.svg)](https://github.com/kostyk348/regd/actions/workflows/tests.yml)
[![Release](https://img.shields.io/github/v/release/kostyk348/regd?sort=semver&color=blue)](https://github.com/kostyk348/regd/releases)
[![Last commit](https://img.shields.io/github/last-commit/kostyk348/regd?branch=master)](https://github.com/kostyk348/regd/commits/master)

`regd` — реестр, в который инструмент попадает **только после рукопожатия**, живёт **на аренде**,
которая истекает, и уходит из выдачи в **архив `expired`** с причиной и датой, а не исчезает молча.
Вызывающий оставляет исход вызова, из исходов считается **репутация числом**. Одна и та же логика
доступна двумя машинными входами: CLI (`--json`) и HTTP-фасад (`serve`).

Ноль зависимостей: только стандартная библиотека Python 3.11+.

**Статус:** MVP собран и проверен запуском, а не описанием.

```
$ python3 -m unittest discover -s tests -t .
Ran 106 tests in 61.803s

OK

$ python3 -m regd demo          # сценарий до/после `gc` одной командой (вывод ниже)
```

## Откуда идея

Задача выросла из дайджеста музея потерянных идей
[«RFC-кладбище»](https://kostyk348.github.io/lost-tech-museum/digests/rfc-graveyard/)
(данные — `lost-tech-museum/data/rfc-graveyard.json`), и три его записи задают три правила реестра:

* **`uddi`** — «UDDI и UDDI Business Registry — публичный каталог бизнесов» (2000–2006). Публичный
  реестр сервисов без модерации, без денег за хостинг и без срока годности записи превратился в свалку:
  50 000 записей, живых — единицы, 12 января 2006 публикацию выключили.
  *Питч записи:* «Реестр агентных инструментов без модерации повторит UDDI (…) Нужны проверка,
  репутация и срок годности записи». → В regd запись — **аренда**: она живёт, пока владелец её
  продлевает (то же правило, что в `hubd` для подписок), и уходит из выдачи в архив с причиной.
* **`whoispp`** — «WHOIS++ и CRISP — распределённый справочник» (1995–2004). Структурный доступ к
  реестру проиграл текстовому WHOIS, и только RDAP (2015) реализовал ту же идею заново.
  *Питч записи:* «Не парсить человеческий текст: если агент разбирает whois-вывод или README реестра,
  требуйте структурный API». → У regd два **машинных** входа и `--json` у каждой команды; ни одна
  функция не разбирает человеческий вывод, а `POST /report` отказывает форме `application/x-www-form-urlencoded`.
* **`webintents`** — «Web Intents — выбрать исполнителя вместо endpoint» (2010–2013). W3C свернула
  работу, но выбор исполнителя в рантайме — ровно модель для агентов.
  *Питч записи:* «Модель намерения вместо вызова: не „дёрни этот endpoint“, а „нужен перевод текста“».
  → `regd find --verb pdf.summarize` ищет по **возможности**, а не по имени сервиса, и отдаёт
  репутацию числом, а не звёздочками.

Из `hubd` (соседний проект в этой же рабочей папке) переиспользованы проверенные приёмы: рукопожатие
с проверкой намерения, аренда с истечением, честный отказ вместо «наверное работает», журнал в JSONL.

## Быстрый старт

Пять команд на живом инструменте. Инструмент для опытов запускается рядом (это тот же фальшивый
инструмент, что используется в тестах и демо):

```bash
# 1. инструмент на loopback, который умеет pdf.summarize и pdf.extract

python3 -m regd.tools --name pdf-summarizer --verb pdf.summarize --verb pdf.extract --port 8080

# 2. регистрация: реестр дёргает endpoint с challenge, инструмент обязан его вернуть

python3 -m regd register --name pdf-summarizer --endpoint http://127.0.0.1:8080 \
    --verb pdf.summarize --verb pdf.extract --owner алиса --lease 3600
```

```

  endpoint http://127.0.0.1:8080   возможности: pdf.summarize, pdf.extract
  рукопожатие подтверждено (поле challenge в JSON); аренда 59м 59с, до 2026-10-14 19:43:18
```

## Что именно решает

| Правило | Как это сделано в коде |
|---|---|
| Каталог — обязательство, а не список (`uddi`) | запись = **аренда** (`--lease`, по умолчанию 3600 с, максимум 30 суток); часы решают, жива ли запись |
| Регистрация только по доказательству | `register` шлёт `challenge` на endpoint инструмента и требует его обратно; не подтвердил — записи нет (код возврата 3) |
| Честный отказ вместо «наверное работает» | не ответил на проверку живости → запись помечена `alive: false` и остаётся в выдаче; три провала подряд → метка `degraded` с причиной |
| Репутация числом, а не звёздочками | `reputation = доля успехов × свежесть` (см. ниже) — в JSON, в списке и в HTTP-ответе |
| Структура вместо парсинга текста (`whoispp`) | `--json` у всех команд; HTTP-фасад принимает только JSON и отказывает форме-урлкодированию |
| Выбор исполнителя в рантайме (`webintents`) | `find --verb pdf.summarize` (точное совпадение возможности) и `--verb 'pdf.*'` (шаблон), сортировка по репутации |
| Мусор не удаляется молча | `gc` переносит протухшую запись в `expired` с причиной, датой, историей исходов; повторный `gc` идемпотентен |
| Одна логика, два входа | CLI и `serve` вызывают одни и те же методы `Registry`: HTTP ничего не решает сам |
| Продление — это подтверждение | `renew` повторяет рукопожатие: «продлил» значит «инструмент жив и это действительно он» |

## Протокол инструмента (как зарегистрировать свой)

Инструменту нужно два эндпоинта на его базовом URL:

| Метод и путь | Что должен сделать инструмент |
|---|---|
| `POST /regd/handshake` | принять JSON `{"regd": "handshake", "challenge": "...", "name": ..., "verbs": [...], "lease_seconds": N}` и вернуть `challenge` обратно (любой 2xx) |
| `GET /regd/health` | ответить любым 2xx, если инструмент жив |

Вернуть challenge можно тремя способами (реестр принимает все три):

* полем `"challenge"` в JSON-ответе;
* заголовком `X-Regd-Challenge`;
* телом-эхо: тело ответа ровно равно строке challenge.

Минимальный инструмент на stdlib (~20 строк):

```python
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
import json

class Tool(BaseHTTPRequestHandler):
    def log_message(self, *a): pass
    def _json(self, code, payload):
        body = json.dumps(payload).encode()
        self.send_response(code); self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body))); self.end_headers(); self.wfile.write(body)
    def do_POST(self):
        raw = self.rfile.read(int(self.headers.get("Content-Length", 0) or 0))
        challenge = json.loads(raw or b"{}").get("challenge", "")
        self._json(200, {"challenge": challenge, "ok": True})     # подтверждаем намерение
    def do_GET(self):
        self._json(200, {"ok": True})                             # /regd/health: жив

ThreadingHTTPServer(("127.0.0.1", 8080), Tool).serve_forever()
```

## Команды CLI

| Команда | Что делает |
|---|---|
| `regd register --name … --endpoint … --verb … [--verb …] [--owner …] [--lease N]` | регистрация после рукопожатия; повторная регистрация того же имени на том же endpoint обновляет запись и сохраняет историю исходов |
| `regd find [--verb X] [--live] [--no-probe]` | поиск по возможности (`pdf.summarize` или шаблон `pdf.*`); по умолчанию проверяет живость найденных |
| `regd list [--no-probe]` | состояние: аренда, живость, успехи/провалы, доля, свежесть, репутация, метки, архив `expired` |
| `regd report --id … --ok \| --fail [--note …]` | исход вызова от вызывающего (`--id` принимает id или уникальное имя) |
| `regd renew --id … [--lease N]` | продление аренды с повторным рукопожатием |
| `regd gc` | сборка мусора: протухшее — в `expired` с причиной и датой |
| `regd serve [--host 127.0.0.1] [--port 8766]` | HTTP-фасад над тем же хранилищем |
| `regd demo [--workdir DIR] [--dying-lease N]` | сценарий целиком: до/после `gc` |

Глобальные флаги: `--store PATH` (по умолчанию `./regd.json`, env `REGD_STORE`),
`--journal PATH` (по умолчанию рядом с хранилищем, env `REGD_JOURNAL`), `--json`.

Коды возврата: `0` — получилось, `2` — ошибка ввода, `3` — отказ по контракту
(рукопожатие не подтверждено, аренда не продлена, записи нет).

## HTTP-фасад

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/healthz` | `{ok, tools, live, lapsed, degraded, expired, now}` |
| `GET` | `/tools` | все записи (без проверки живости) |
| `GET` | `/find?verb=…[&live=1][&probe=1]` | найденные исполнители; без `verb` — 400 (структурный вход, а не «покажи всё и я поищу») |
| `POST` | `/report` | JSON `{"id": …, "ok": true|false, "note": "…"}`; неизвестный id — 404, не-JSON тело — 400 |

## Как считается репутация

```
доля успехов = успехи / (успехи + провалы)        # исходов нет → 0.5 (нейтрально, а не 0)
свежесть     = exp(-возраст · ln 2 / 12 часов)    # возраст — от последнего исхода или продления аренды
репутация    = округление до 0.001 (доля успехов × свежесть)
```

Одна формула, ноль магии: в JSON видны все множители (`ok`, `fail`, `success_ratio`, `freshness`,
`reputation`), поэтому «почему этот исполнитель первый» проверяется арифметикой, а не доверием.

Метка `degraded` (запись остаётся в выдаче, но помечена и объяснена) ставится, когда:

* три проверки живости подряд без ответа;
* рукопожатие не подтверждено (неудачный `register` существующей записи или `renew`);
* доля успехов ниже 0.2 при пяти и более исходах от вызывающих.

Метки лечатся: инструмент ответил — причина ушла, `degraded` снят.

## Чего в MVP нет

Осознанно не делаем, чтобы не расползалось: авторизации, TLS и мультитенантности (это loopback/интранет-инструмент),
БД (хватает JSON-файла с атомарной записью — `os.replace` после `fsync`), веб-интерфейса,
интеграции с настоящими MCP-серверами (следующий шаг, отдельной задачей).

## Тесты и CI

```bash
python3 -m unittest discover -s tests -t .        # 106 тестов, зелёные
```

Покрыты правила, а не строки: отказ регистрации без рукопожатия, истечение аренды и `gc`
(в том числе «запись осталась в архиве с причиной»), поиск по возможностям и шаблону, пересчёт
репутации, недоступный инструмент помечен, но не пропадает из выдачи, продление без подтверждения
отклоняется, HTTP-фасад отказывает не-JSON телу, демо-сценарий до/после `gc`.

CI — `.github/workflows/tests.yml`: тот же прогон на Python 3.11 / 3.12 / 3.13, без установки
зависимостей (их нет).

## Правила, по которым собран проект

* Только стандартная библиотека: `pip install` в этом репозитории не нужен.
* «Работает» подтверждается выводом команды; не работает — пишем, что не работает.
* Тесты зелёные перед каждым коммитом, сообщения в стиле `<область>: <что изменилось>`.
* Музей потерянных идей — только чтение: данные (`data/`) пишет хранительница архива, стеки
  (`stacks/`) — витрина карточек; здесь на записи архива только ссылаются по `id`.

Соседний проект того же автора — [`hubd`](https://github.com/kostyk348/hubd): хаб подписок и сканер
источников; `regd` вырос из его приёмов (рукопожатие, аренда, честный отказ, журнал JSONL).
